# コントローラー送信の遅延測定

ブリッジを起動し、このクライアントを開いてコントローラーを接続します。
接続先は `src/App.tsx` の `GrpcProvider` に設定されています。
別途 ROS echo ノードを起動する必要はありません。ブリッジ自身の
DynamicSubscription が `/joy` の送信メッセージを受信します。

画面には以下の区間を表示します。

- Publish 応答まで: Gamepad 状態の取得直前から Publish RPC 完了まで。
  JSON encode、通信、サーバーの JSON decode、ROS publish 呼び出し、応答通信を含みます。
  他の ROS ノードでの受信・処理完了を示す値ではありません。
- ROS subscription 経由の往復: 同じ開始点から `/joy` の受信 JSON の decode・照合まで。
  サーバーの DynamicPublisher → ROS → DynamicSubscription → JSON encode → broadcast →
  gRPC stream → ブラウザの経路を含みます。ロボットの制御処理や画面描画は含みません。

両区間ともブラウザの `performance.now()` の差で計算します。端末間の時計の
同期は不要です。片道遅延を示すものではなく、往復値の半分を片道値とは見なしません。
コントローラーの物理入力、OS の入力処理、次の10msタイマーを待つ時間も対象外です。

照合用に Joy の `header.stamp` へブラウザの壁時計を設定します。同一ミリ秒の送信は
nanosec を増やして区別し、受信時には未完了の stamp に一致するメッセージのみ採用します。
frame_id は空文字です。stamp は ROS simulated time ではありません。
他のノードが同じ stamp のメッセージを再送する環境では最初の一致が採用されます。

送信は10msタイマー（目標100Hz、正確な周期の保証なし）。最大100件の RPC が同時進行し、
上限到達時と非表示タブでは送信をスキップします。RPC の期限は5秒です。
往復も5秒で打ち切ります。「5秒以内に未受信」は discovery、通信エラー、遅延、
購読切断なども含み、ROS のメッセージ損失率そのものではありません。
Publish失敗と未受信は別集計なので同じ送信が両方に含まれることがあります。

統計は経路ごとに成功した直近最大1000件、表示更新は250ms間隔です。
初回接続・DDS discovery の時間は除外していません。安定時を比較するなら十分に送信を
続けて初期サンプルが窓から外れた後の値を使い、未受信件数も併記してください。
コントローラー切断時は停止して最終表示を保持し、再接続時に新しい測定を開始します。
購読エラーは表示されますが、自動再接続は行いません。

確認手順: `npm run build` 後に `npm run preview -- --host` などで配信し、
Gamepad API の使える HTTPS / localhost 環境で開きます。送信数、往復受信数、
両経路の統計が増えることを確認してください。ネットワーク越しの値は実機で測定が必要です。
